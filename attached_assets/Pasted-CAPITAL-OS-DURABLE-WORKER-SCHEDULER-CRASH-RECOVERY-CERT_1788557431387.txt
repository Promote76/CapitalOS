==================================================
1. ARCHITECTURE
==================================================

Implement or complete a PostgreSQL-backed durable job system.

Required lifecycle:

PENDING
→ LEASED
→ RUNNING
→ SUCCEEDED

Failure lifecycle:

RUNNING
→ RETRY_PENDING
→ LEASED
→ RUNNING

Terminal failure:

RUNNING
→ DEAD_LETTER

Recovery:

LEASED/RUNNING
→ stale lease detected
→ RECOVERABLE
→ RETRY_PENDING

Use database state as the source of truth.

In-memory queues must not be authoritative.

==================================================
2. JOB MODEL
==================================================

Ensure durable job records contain sufficient fields similar to:

id
householdId
jobType
payloadReference
status
priority
attemptCount
maxAttempts
availableAt
leaseOwner
leaseExpiresAt
startedAt
completedAt
lastError
idempotencyKey
correlationId
createdAt
updatedAt

Do not store secrets in job payloads.

==================================================
3. ATOMIC LEASING
==================================================

Workers must claim jobs atomically.

Multiple workers competing for the same job must never
simultaneously own it.

Use appropriate PostgreSQL transactional locking semantics.

Certify with concurrent worker tests.

==================================================
4. LEASE EXPIRATION
==================================================

Every claimed job must have a lease.

If Worker A crashes:

the job must not remain permanently RUNNING.

After lease expiration:

another authorized worker may recover it according to policy.

Never allow two valid leases simultaneously.

==================================================
5. HEARTBEATS
==================================================

Implement worker heartbeat state.

Track:

workerId
startedAt
lastHeartbeatAt
currentJob
status
version

Detect stale workers.

Expose worker health to internal operations.

==================================================
6. CRASH RECOVERY
==================================================

Execute an actual crash test.

Required scenario:

create durable job
→ Worker A leases job
→ Worker A begins processing
→ forcibly terminate Worker A
→ wait/detect stale lease
→ start Worker B
→ Worker B recovers job
→ authoritative state reconstructed
→ job safely completes

Produce runtime evidence.

Source inspection does NOT count.

==================================================
7. IDEMPOTENCY
==================================================

Crash recovery must not create duplicate economic effects.

For every job capable of affecting:

financial calculations
reservations
reconciliation
audit
execution state
provider synchronization

require idempotency.

Test:

perform effect
→ crash before acknowledgement
→ retry job

Expected:

ONE economic effect

not two.

==================================================
8. RETRY POLICY
==================================================

Implement bounded retries.

Support:

attemptCount
maxAttempts
backoff
retry classification

Differentiate:

TRANSIENT
PERMANENT
UNKNOWN

Transient examples:

temporary DB contention
temporary provider failure
network timeout

Permanent examples:

invalid payload
unauthorized operation
invalid state transition

Permanent failures should not retry indefinitely.

==================================================
9. EXPONENTIAL BACKOFF
==================================================

Use bounded exponential backoff with jitter where appropriate.

Do not create retry storms.

Persist next available execution time.

==================================================
10. DEAD-LETTER QUEUE
==================================================

After maxAttempts:

move job to DEAD_LETTER.

Preserve:

original job
error history
attempt history
correlation ID
household
job type
timestamps

Never silently discard failed jobs.

Follow the existing Capital OS light UI.

==================================================
12. OPERATOR REPROCESSING
==================================================

Allow authorized operators to reprocess appropriate
DEAD_LETTER jobs.

Reprocessing must:

require authorization
create audit evidence
retain original failure history
preserve idempotency
never bypass Guardian/risk/execution controls

Do not allow arbitrary payload editing and replay.

==================================================
13. SCHEDULER
==================================================

Implement or complete a durable scheduler.

Scheduled work must survive:

API restart
worker restart
scheduler restart

Schedule definitions must be persistent.

Do not depend solely on:

setInterval()
setTimeout()
browser state
single-process memory

==================================================
14. SCHEDULER LEADERSHIP
==================================================

Multiple application instances must not produce duplicate
scheduled work.

Implement deterministic leadership/locking or equivalent
database-backed coordination.

Test two scheduler instances simultaneously.

Expected:

ONE scheduled job

not two.

==================================================
15. MISSED SCHEDULE RECOVERY
==================================================

Test:

scheduler expected to fire
→ scheduler unavailable
→ scheduled time passes
→ scheduler restarts

System must apply explicit policy:

CATCH_UP

or

SKIP

according to job type.

Never silently lose required work.

==================================================
16. EXECUTION-SAFETY INTEGRATION
==================================================

Any future execution-related background job must consult:

Execution Control
Guardian
Risk Governor

before creating additional exposure.

Worker recovery must NEVER infer:

ACTIVE

from stale execution state.

If execution state cannot be verified:

FAIL CLOSED.

==================================================
17. STOP DURING JOB
==================================================

Test:

job begins
→ Execution Control transitions to STOP
→ job reaches next safety boundary

Expected:

no new exposure is created.

STOP must dominate worker continuation where applicable.

==================================================
18. GUARDIAN FAILURE DURING JOB
==================================================

STALE
UNAVAILABLE
STOP
DISAGREEMENT

during an execution-capable workflow.

Expected:

no new exposure.

==================================================

Add cross-household tests.
