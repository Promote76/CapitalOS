==================================================
1. AUTHORITATIVE EXECUTION STATE
==================================================

Create one server-authoritative execution state machine.

Required states:

DISABLED
MICRO_LIVE_ELIGIBLE
MICRO_LIVE_ARMED
MICRO_LIVE_ACTIVE
SAFE_MODE
STOP
EVACUATE
LOCKED

Default:

DISABLED

Persist the authoritative state in PostgreSQL.

The browser is NEVER the source of truth.

==================================================
2. HOUSEHOLD SCOPE
==================================================

Execution state must be household scoped.

Every read and transition must derive household identity from:

authenticated actor context

NOT:

request.body.householdId
query parameter
frontend state
demo household
seeded household

Attempted cross-household execution-state access must fail closed.

==================================================
3. EXECUTION CONTROL RECORD
==================================================

Create an authoritative persistence model similar to:

ExecutionControl {
  id
  householdId
  state
  version
  reason
  changedBy
  changedAt
  correlationId
  createdAt
  updatedAt
}

Add required indexes and uniqueness constraints.

Use optimistic or pessimistic concurrency control.

Two simultaneous transitions must not corrupt state.

==================================================
6. STOP SEMANTICS
==================================================

STOP must mean:

NO NEW ORDER INTENTS
NO NEW ORDER SUBMISSIONS
NO NEW STRATEGY ACTIVATION
NO CAPITAL SCALE-UP

Where execution infrastructure exists:

attempt cancellation of resting orders according to policy.

STOP must NOT:

erase evidence
silently liquidate positions
increase exposure
change capital limits
permit AI override

==================================================
7. EVACUATE SEMANTICS
==================================================

EVACUATE is more severe than STOP.

It must:

block new exposure
request cancellation of resting orders
surface existing inventory
prepare controlled inventory reduction

Do NOT automatically dump positions at market.

Any flattening mechanism must remain governed by:

liquidity
slippage
order-size limits
risk policy
human authorization where required

==================================================
8. LOCKED SEMANTICS
==================================================

LOCKED must require explicit authorized recovery.

Strategy code cannot unlock it.

AI cannot unlock it.

Automation cannot unlock it.

Browser reload cannot unlock it.

Application restart cannot unlock it.

==================================================
12. AUTHORIZATION
==================================================

Emergency STOP should favor safety.

An appropriately authenticated authorized operator must be able
to STOP execution immediately.

Increasing execution authority requires stricter permission.

For example:

STOP:
authorized operator

ARM:
Owner + required permission + recent auth

ACTIVE:
Owner + required permission + all gates

UNLOCK:
Owner + recent auth + recovery conditions

Do not allow authentication strength to increase authorization.
