FINAL ENGINEERING PRINCIPLE

Capital OS is already capable of sophisticated calculations.

The question in this sprint is no longer:

Can the system calculate capital?

The question is:

Can one household ever alter another household?

Can two simultaneous requests corrupt money?

Can an unauthorized browser origin create a financial write?

Can the database be recreated and upgraded safely?

Can the platform recover from data loss?

Can we prove these properties through HTTP,
PostgreSQL,
authentication,
browser,
security,
and concurrency tests?

The acceptable design is:

AUTHENTICATED USER
        ↓
SERVER-RESOLVED HOUSEHOLD
        ↓
EFFECTIVE PERMISSION
        ↓
HOUSEHOLD-SCOPED OBJECT
        ↓
VALIDATED REQUEST
        ↓
ATOMIC DATABASE TRANSACTION
        ↓
AUDIT
        ↓
PERSISTED RESULT
        ↓
VERIFIED TEST

Capital OS must never depend on:

Client honesty
Hidden buttons
Guessable IDs
Local-only financial state
Application-level race assumptions
Documentation without execution evidence

The goal of this sprint is not more features.

The goal is:

ZERO KNOWN P0 TRUST-BOUNDARY DEFECTS

Fix, test, prove, and document accordingly.
