Executive Summary

Capital OS organizes an approximately $250 weekly rhythm around a first duplex acquisition: $200 Duplex Reserve, $25 Capital OS, and $25 Opportunity Reserve. The product combines household finance, protected goals, Treasury governance, business separation, property decision support, accounting, operations, advisory intelligence, and research-only strategy workflows.

The strongest evidence is in the financial domain: PostgreSQL decimal money, integer-cent decisions, protected-capital rules, exact allocation arithmetic, ledger movements, and disabled-by-design execution boundaries. The weakest evidence is at the production boundary.

  • Release blocker: a caller-supplied contribution goal ID is not constrained to the current household and can update a foreign goal.
  • Release blocker: write-origin enforcement is conditional on deployment configuration and has no CSRF token or explicit same-site policy.
  • Migration reproducibility, backup/restore, durable scheduling, and recovery are documented but not proven operationally.
  • There are no HTTP integration, database integration, authenticated browser E2E, or true concurrency tests.
  • Several visible actions are prepared, simulated, read-only, or local-only rather than authoritative writes.

Current implementation

Identity boundary

Clerk browser and API middleware are wired. External Clerk identities resolve to internal users and active household memberships. Production unauthenticated routes return 401; the development role header does not bypass this boundary.

Financial boundary

Money is stored as PostgreSQL numeric(18,2) and calculated as integer cents. Contributions, transfers, goals, Treasury requests, audit events, and idempotency records are persisted where supported.

Business boundary

Business operating cash, revenue, expenses, reserves, and proposed distributions are separated from household deployable capital. A completed reviewed owner-distribution bridge is not yet implemented.

Execution boundary

Strategy Lab is research-only. Micro-Live rehearsal and review records persist, but real venue registration and order transmission are disabled. AI and automation cannot move protected capital.

Technical architecture

The intended request path is:

Clerk session → internal user → active membership → request household context → Express route → Zod validation → domain service → Drizzle transaction → PostgreSQL → audit/idempotency result

OpenAPI is the contract source and Orval generates React Query and Zod artifacts. Pino structured logs and correlation IDs exist. Liveness is independent of PostgreSQL and readiness returns 503 when PostgreSQL is unavailable. The API does not run startup DDL.

The managed database flow is intentionally conservative: generated SQL is reviewed, development uses the supported managed push flow, and production schema changes use Publish. The repository still lacks a reproducible migration history test from zero, an existing-schema upgrade test, a rollback/forward-fix execution record, and a restore drill.

Finance, accounting, and business

Safe-to-Deploy is calculated from liquid accounts, bills, essential expenses, reserve shortfall, protected commitments, upcoming required expenses, a safety buffer, and a deployable percentage cap. Business cash, protected Duplex Reserve, planning balances, receivables, property estimates, projected income, and unrealized results are not valid spendable sources.

Accounting is service-backed but incomplete: real-estate and investment fields are limited, business equity treatment differs between views, liabilities are incomplete, and an empty ledger can be interpreted as reconciled. The system avoids double-counting current net worth by using included financial-account balances while keeping planning and business cash separate.

The weekly contribution path records allocation metadata, ledger movements, duplex goal progress, and audit data. It remains blocked from release until every supplied goal ID is verified against the current household.

Micro-Live, AI, and operations

Micro-Live transmission: DISABLED BY DESIGN.

The simulated adapter refuses place/cancel, the reviewed adapter registry is empty, and rehearsal reports no transmission. Remaining issues include an order-event relationship mismatch, missing persisted event-sequence validation, nullable external event IDs, and incomplete durable reconciliation failure handling.

AI recommendations persist as advisory records and cannot move money, change protection, override risk, enable trading, change credentials, sign contracts, or submit transactions. Automation validates a safe action list and records prepare-only runs, but no durable scheduler or worker exists and automation failure health is currently hardcoded to zero.

Top remaining risks

  1. Cross-household goal mutation through contribution input.
  2. Fail-open browser write-origin and CSRF boundary.
  3. No proof of multi-household HTTP authorization or IDOR resistance.
  4. No reproducible managed migration and upgrade test.
  5. No operational backup/restore drill.
  6. Concurrent transfer balance race.
  7. Role-only enforcement ignores stored membership permissions; step-up is absent.
  8. No durable scheduler, retry, or restart recovery.
  9. Accounting/business equity and liability incompleteness.
  10. Micro-Live event and reconciliation durability gaps.

Maturation path

Continue hardening. First fix household-scoped authorization and origin controls, then add authenticated two-household HTTP fixtures, migration/upgrade tests, an isolated restore drill, atomic transfer concurrency tests, effective permissions, step-up authentication, durable operations, and operational telemetry.

Do not add real bank aggregation, automated ACH, external investor funds, live trading, autonomous AI execution, or blockchain submission until the P0 and P1 trust boundaries are evidenced.
