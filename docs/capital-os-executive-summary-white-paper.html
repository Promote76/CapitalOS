01 · Executive summary

Capital OS turns household surplus into governed, purpose-led capital.

Capital OS is a light-theme family-capital workspace for disciplined saving, protected reserves, property acquisition planning, business-income separation, strategy research, Treasury allocation, and operational review. Its central idea is simple: household cash is not automatically deployable capital.

The product is organized around a first duplex acquisition funded by an approximately $250 weekly rhythm: $200 to a protected Duplex Reserve, $25 to Capital OS, and $25 to an Opportunity Reserve. The interface presents a calm family-office control surface rather than a trading terminal. Green communicates protection and progress, blue active capital, lavender research/opportunity, amber review, and red critical safeguards.

Bottom line. The application has a credible safety-first foundation: exact-cents financial logic, PostgreSQL persistence, server-side governors, audit and idempotency concepts, operational approvals, a business-capital boundary, and a deliberately disabled Micro-Live execution boundary. It is not yet a production-grade multi-user financial platform because identity, tenant isolation, migration discipline, route-level integration coverage, and several user-facing workflows remain incomplete.

02 · Product overview

One workspace for the household capital lifecycle.

Capital OS links household finance to protected goals without collapsing their meanings. It can calculate, explain, remind, review, queue, and recommend. It intentionally does not move money, pay bills, sign contracts, connect a bank without an approved provider path, or enable trading.

03 · Current implementation state

What is real, what is intentionally bounded, and what still needs productization.

Data-backed foundation

PostgreSQL and Drizzle are the source of truth for household, capital, finance, Treasury, property, strategy, governance, operations, business, and Micro-Live records. Generated OpenAPI clients and Zod schemas connect the React UI to the Express API.

Demo and review surfaces

The approved UI remains usable when a backend read is unavailable, but local fallback data and feedback-only buttons can make a presentation surface look more complete than its persistence path.

Business Engine slice

The current Business page and API separate operating-company revenue, expenses, reserves, cash, owner pay, distributions, and ownership-adjusted equity. Distribution requests are review-only and reserve floors are enforced.

Development identity

Development defaults to the seeded Morgan household owner and can exercise role paths with X-Household-Role. Production defaults to viewer until an authenticated household identity bridge is implemented.

Interpretation rule. “Visible in the UI” does not always mean “persisted in PostgreSQL.” The most important examples are several Dashboard quick actions, some Portfolio/Risk/Settings actions, accounting review/export affordances, and the contribution display’s current tendency to label API contributions as Duplex Reserve.
04 · Technical white paper

Architecture and system boundary

Capital OS is a pnpm workspace with two primary runtime artifacts: a React/Vite web application and an Express API server. A separate mockup-sandbox artifact supports component previews and visual exploration.

Browser / React UI │ generated React Query client ▼ Express 5 API ── security headers · rate limit · CORS · write-origin boundary · pino logging │ generated Zod request/response validation ▼ Domain services ── finance · Treasury · property · strategy · business · accounting · OMS · governance │ Drizzle transaction boundary ▼ PostgreSQL ── household-scoped records · ledger · audit · idempotency · operational state │ └── no bank credentials · no autonomous payments · no live venue transport · no blockchain submission

The API contract is defined in lib/api-spec/openapi.yaml. Orval generates the React Query client in lib/api-client-react and Zod schemas/types in lib/api-zod. The intended path is documented as React UI → generated client → Express route → Zod validation → domain service → Drizzle/PostgreSQL → audit event.

Data model

The schema is organized by bounded financial and governance domains rather than by screens:

  • Identity and tenancy: users, households, members, roles, and household settings.
  • Household finance: provider-neutral bank connection state, financial accounts, categories, signed transactions, recurring commitments, bills, upcoming expenses, income sources, reserves, and snapshots.
  • Capital and ledger: internal capital accounts, goals, allocation rules, contributions, transfers, ledger transactions, and ledger entries.
  • Treasury: prioritized buckets, policy, reservations, capital requests, health, liquidity ladders, and stress cases.
  • Property: goals, markets, candidates, buy boxes, financing, preapproval records, documents, milestones, readiness, and underwriting.
  • Strategy and intelligence: strategies, immutable versions, performance, experiments, journal entries, recommendations, insights, and feedback.
  • Governance and operations: risk states/events, append-only audit events, idempotency keys, tasks, approvals, alerts, automations, runs, and preferences.
  • Business: entities, ownership, business-linked accounts, revenue, expenses, reserves, and distributions.
  • Micro-Live: policy, venue state, sessions, order intents/events, fills, positions, reconciliation, Guardian heartbeats, incidents, reviews, and reactivation requirements.

Authoritative money uses PostgreSQL numeric(18,2). Service calculations convert validated decimal strings into integer cents and format back to decimal strings at the API boundary. Trading quantities and prices use a finer numeric scale. Calendar dates use date columns rather than timezone-shifting timestamps.

Household finance and Safe-to-Deploy

Household finance is deliberately read-only with respect to external institutions. Manual entry and CSV-first workflows are provider-neutral. The Capital Governor is the boundary between household context and deployable internal capital.

  • Safe-to-Deploy is clamped at zero.
  • It is reduced by bills, essential expenses, emergency-reserve shortfall, protected-goal commitments, known upcoming expenses, and the configured safety buffer.
  • It is additionally bounded by the Governor’s maximum deployable percentage and confidence in the underlying data.
  • Protected capital stays ring-fenced and cannot fund experimental allocation while the protected lock is active.
  • Household finance cannot ACH, pay bills, trade, or store bank credentials. The Plaid adapter is disabled until an approved connection exists.

Treasury and capital governance

Treasury models a hierarchy of obligations, operating cash, emergency reserve, protected duplex capital, closing costs, opportunity reserve, liquid Treasury, and validated strategy capital. It calculates health, utilization, liquidity coverage, emergency coverage, stress outcomes, reservations, and safe deployment. Capital requests are submitted for human decision; they do not pull funds directly.

The Capital Governor enforces minimum cash, active-capital and strategy-allocation limits, protected-capital locks, weekly risk and drawdown ceilings, and emergency stop state. The UI explains these decisions rather than treating a recommendation as authority.

Business and operating-company boundary

The Business Engine extends Capital OS without merging business and household books. Revenue and expenses are recorded against a business entity; business-linked accounts provide operating cash; reserve targets, tax reserve, and safety buffer establish a distribution floor; ownership percentage determines the household’s share of business equity.

Accounting principle. Owner contributions and intercompany transfers are not revenue. Owner distributions are not ordinary operating expenses. Business cash never becomes household Safe-to-Deploy directly. Only a completed, human-reviewed distribution can become household income. The system must include either underlying business assets or an ownership-adjusted business equity value in household net worth—not both.

Strategy Lab and Micro-Live

Strategy Lab is a research environment. It supports hypotheses, immutable versions, deterministic backtests/walk-forward/shadow/paper experiments, execution friction, regime metrics, drawdown events, journals, and evidence-based graduation. Promotion is sequential and requires observations, reconciliation accuracy, and no critical errors. No strategy stage enables live trading in the current release.

Micro-Live is a fail-closed control plane, not a live trading product. The default policy is a small sandbox with separate venue, strategy, exposure, order, and loss caps. Household and protected capital are inaccessible. The simulated adapter always refuses order transmission. A future real venue would require a reviewed server-side adapter, opaque credential reference, isolated execution account, market allowlist, security/jurisdiction/terms review, disabled withdrawals, venue-authoritative reconciliation, and explicit owner arming.

OMS state handling models partial fills, cancel/fill races, rejection, expiration, unknown state, duplicate orders/fills, recovery, and reconciliation mismatch. Guardian may stop, lock, request cancel-all, and alert a human, but may not trade, increase capital, or change policy.

AI and Operations

AI is advisory-only. It may summarize patterns, flag anomalies, identify recurring expenses, and recommend a review. It cannot approve transactions, move capital, change a protected goal, connect a bank, pay a bill, override risk, enable trading, change credentials, sign contracts, or submit blockchain transactions. Human approval records intent and audit; it does not create an external payment.

Operations provides the current safe automation surface: tasks, approvals, alerts, prepare-only automation runs, notification channels, and quiet hours. Safe automation may prepare reviews, tasks, alerts, or reports. Restricted actions include transfers, protected-capital changes, trading enablement, ownership changes, offer submission, contract signing, and security disabling.

05 · Reliability, security, and operations

Controls are strongest at the domain boundary, not yet at every platform boundary.

Implemented controls

  • Server-side permission checks for owner, partner, advisor, and viewer paths.
  • Exact-cents financial calculations and fixed-precision database money.
  • Transactional ledger and audit writes for protected capital movements.
  • Household-scoped idempotency for contributions and transfers, including conflict detection for key reuse with a different amount.
  • Protected-capital locks, reserve floors, bounded allocations, emergency stop, and fail-closed execution checks.
  • Append-only audit event concepts, reason/evidence fields, human decision records, incident reviews, and reactivation requirements.
  • Security headers, disabled x-powered-by, structured pino request logging with sensitive-header redaction, an in-memory rate limit, CORS configuration, and a write-origin boundary.
  • Advisory-only AI and no external bank, venue, chain, payment, or contract execution in the current boundary.

Highest-priority gaps

  1. Authentication and tenant isolation. Clerk dependencies, managed keys, and a proxy template are present, but middleware wiring, browser provider, sign-in routes, authenticated user resolution, and user-to-household mapping are not complete. Development accepts a role header; production falls back to a seeded viewer. This is the largest gap between the safety model and a deployable multi-user product.
  2. Deployment health and schema lifecycle. The health endpoint is dependency-free liveness, not database readiness. There is no versioned migration history or rollback workflow visible; development schema changes use Drizzle push, while production schema changes must be applied through Publish. Startup seeding and fixed demo data require strict environment separation.
  3. Integration and contract verification. Pure domain tests are strong, but route, database, HTTP contract, browser end-to-end, load, and security coverage is limited. OpenAPI is the source of truth by convention; route/codegen parity is not visibly CI-enforced.
  4. Execution and automation observability. Micro-Live remains safely disabled, but real venue transport and independent Guardian runtime are future work. Operations currently reports automation failures as zero rather than deriving them from run records, and no scheduler/queue for periodic reconciliation or automation is evident.
  5. Accounting completeness. Accounting calculations and reconciliation views are valuable, but investment growth is currently incomplete, there is no universal posting abstraction or database-level double-entry invariant, and multi-line journal semantics should be clarified.
  6. Product truthfulness. Several visible controls are feedback-only or local-state. The application should distinguish clearly between persisted actions, prepared reviews, and presentation affordances.
Do not infer production authorization from the UI. The Micro-Live readiness score, owner-only visual controls, and role labels are not substitutes for authenticated identity, step-up verification, independent review, or a separately reviewed deployment boundary.
06 · Verification and engineering state

Current evidence supports the safety foundation, with important scope limits.

The current repository contains a broad TypeScript workspace with React/Vite frontend code, Express API code, Drizzle/PostgreSQL schema, generated API artifacts, and domain tests. The latest recorded feature verification includes:

  • API and frontend TypeScript typechecks passing.
  • Frontend and API production builds passing when supplied with required runtime configuration.
  • Generated OpenAPI, Zod, React Query, and TypeScript clients regenerated from the contract.
  • Development database schema pushed successfully.
  • 62 of 62 direct API domain tests passing after the Business Engine slice was added.
  • Running API and web workflows with successful runtime requests and responsive Business, Operations, and other reviewed pages.

The direct test command is intentionally focused on artifacts/api-server/src/domain/*.test.ts. That gives high confidence in deterministic calculations and state-machine rules, but it does not prove production behavior across authentication, routes, database transactions, browser flows, concurrency under load, or deployment recovery.

07 · Recommended maturation path

Sequence production hardening before expanding execution capability.

  1. Complete authenticated identity and household resolution. Wire Clerk at the API and browser boundaries, map authenticated users to household memberships, remove privilege-by-header outside explicit test mode, and add authenticated role/tenant tests.
  2. Make the database lifecycle explicit. Establish a versioned migration and rollback strategy, separate development seed repair from production startup, and add readiness checks that report database dependency state.
  3. Close the planning-to-governor integrity loop. Add invariant tests proving that planning balances, property values, business cash, receivables, and unrealized profit cannot silently raise household Safe-to-Deploy without an explicit reconciliation bridge.
  4. Productize the existing surfaces. Replace feedback-only save/export/sync actions with persisted workflows, expose CSV import in Accounts, preserve contribution allocation metadata in the UI, and separate demo fallback state from authoritative state.
  5. Expand integration coverage. Add OpenAPI route parity checks, HTTP contract tests, database transaction tests, browser end-to-end tests for critical capital flows, concurrency tests for seeding and idempotency, and security/load testing.
  6. Improve operational truth. Derive automation failure health from run records, add structured metrics/tracing, implement a durable scheduler/queue for periodic checks, and formalize backup/restore and incident runbooks.
  7. Keep real execution last. If a real venue is ever considered, preserve the current isolation and require independent security, jurisdiction, terms, withdrawal, credential, adapter, reconciliation, Guardian, and human-arming review as a separate release boundary.
08 · Conclusion

A promising governed capital workspace—not yet an autonomous financial platform.

Capital OS already has a differentiated product thesis: protect the family balance sheet first, make capital purpose visible, keep business and household economics separate, and make every higher-risk action reviewable. Its strongest work is in deterministic domain logic and explicit safety boundaries. The current codebase demonstrates that money movement, trading, blockchain, business distributions, and AI authority can be constrained instead of merely described.

The next milestone is not “more automation.” It is trustworthy identity, tenant isolation, production schema discipline, persisted user workflows, and end-to-end verification. Once those foundations are complete, the existing Treasury, Business, Operations, Accounting, property, strategy, and Micro-Live control planes will have a more credible path from polished prototype to production-grade family capital operating system.
